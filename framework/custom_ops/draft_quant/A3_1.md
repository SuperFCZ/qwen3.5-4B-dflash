# A3.1：批量反量化与连续计时

A3 已由用户确认数值验收全通过，实际使用 7 核。旧 `checked-v1` 诊断计时中，gate/up
约 14.31 ms（原生 OM 约 4.05 ms），down 约 7.47 ms（原生约 1.56 ms）。单核→多核已经
达到约 6.85×/6.55×，本阶段降低核内 tile 处理成本。用户已反馈本轮 `continuous-v1`
计时与 msprof 摘要：legacy→batched 约 3.87×，gate/up 约 3.677 ms、down 约 1.91 ms。
完整结果及证据边界见 [A3_RESULTS.md](A3_RESULTS.md)；完整 Draft / Decode 性能仍为 `NOT_RUN`。

## 内核改动

保留 A3 的 N64 分工、K128 流式归约（K=256 tiny 仍为 K256）、FP16 权重反量化、完整 K
的 FP32 累加及最终 FP16 输出舍入。shape 集合、ACLNN/tiling ABI、UB 分配、MatMul 参数和
系统 workspace 均保持原样。不改 Qwen/DFlash 主流程。

INT8 tile 的物理排列可写成 `[tileK/32,64,32]`。对每个 K32 plane，一次 Cast 用 mask=32、
repeat=64 处理全部 N 行：

```text
q offset = k1*64*32 + n*32 + t
w offset = n*tileK + k1*32 + t
src repeat stride = 1 * 32 B
dst repeat stride = (tileK*2/32) * 32 B
```

所有 Cast 完成后，再对每行、每个 group 做一次 128 元素的 FP16 Muls，仍读取
`scale[group*64+n]`，不把 group scale 移到 MatMul 后。

| 每个 N64×K128 tile 的源码级调用 | legacy | batched |
| --- | ---: | ---: |
| Cast | 256 | 4（每次 64 个 repeat） |
| Muls | 256 | 64 |
| PIPE_V barrier | 512 | 2 |

K256 路径分别是 512→8 次 Cast、512→128 次 Muls、1024→2 次 PIPE_V。不同 Cast 写入不重叠
的 K32 区域，不同 Muls 写入不重叠的 N/group 区域；两类操作之间保留 PIPE_V。MTE2→Scalar/
Vector 事件、MatMul 前后及缓冲复用前的 PIPE_ALL 继续保留。本版没有预取、双缓冲或 DMA
合并，也没有改变 K 累加顺序。

接口依据官方 v9.0.0 [Cast](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/Cast.md)、
[UnaryRepeatParams](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/UnaryRepeatParams.md)
和 [dav_m200 实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/basic_api/dav_m200/kernel_operator_vec_vconv_impl.h)。
该实现将 INT8→half 的 CAST_NONE 路径映射到 `vconv_s82f16`。实际 310P3 行为仍以服务器验收为准。

## 新计时协议

`DFLASH_SUITE=a31` 使用 `continuous-v1`。custom ACLNN 与 native OM 共用同一个 C++ 调度器：

1. 两次 correctness：不同 NaN poison、完整输入只读/guards/输出检查，保存 `actual-{0,1}.bin`。
2. 连续 warmup 和测量：每次 launch+stream synchronize，循环内不做 poison、D2H 回读、
   文件写入或输入/输出检查。custom 每次仍申请新的 executor，GetWorkspaceSize 的耗时单列。
3. 检查最后一个 timed 输出、输入和 guards，保存 `benchmark-last.bin`。
4. 再 poison 一次并执行，检查输出和输入/guards，保存 `postcheck.bin`，防止旧的正确输出
   掩盖未写位置。

中间每个 timed 输出没有逐次回读验证；严格正确性回归与前后检查独立保留。结果字段明确记录
该边界，缺少尾部/后置检查或与 correctness 输出不同都会失败。性能是同输入独立调用的
host launch+sync 时间，不等于纯设备 kernel 时间或完整 Draft/Decode 收益。

旧 A2/A3 的 `checked-v1` 仍可使用，但旧数据不能与 `continuous-v1` 直接计算优化加速比。

## 服务器 A/B

保留同一个已通过的 `A2_BUNDLE` 和 `A2_NATIVE_OM_MANIFEST`，不必重新 capture/export。
保留 CANN_ROOT、MODEL_PYTHON、DEVICE_ID 的原设置，在仓库根目录执行：

```bash
git pull --ff-only
export A2_WARMUP=5
export A2_REPETITIONS=30

# 原指令序列 + 新计时协议，作为本次基线。
DFLASH_SUITE=a31 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=legacy \
  bash framework/custom_ops/draft_quant/run_server.sh

# 批量反量化 + 相同计时协议。
DFLASH_SUITE=a31 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=batched \
  bash framework/custom_ops/draft_quant/run_server.sh
```

每次都会 build/package/install 新的隔离 OPP，并运行全部 A1 + 10 组真实投影。两种模式来自
同一源码，仅通过构建期宏选择；host/kernel 使用内容相同的配置 header，配置及哈希留档。
launch 记录会标明 `dequant_mode`，与构建配置不符时失败。A3.1 初始为 version=2，
当前 A3.2 源码使用 version=3 并增加 pipeline 字段，默认 `DFLASH_PIPELINE_MODE=serial`。
当前默认 dequant 模式是 batched。

保存两次打印的 `data/suite.json` 路径，再比较：

```bash
"$MODEL_PYTHON" framework/custom_ops/draft_quant/test/compare_a31.py \
  --baseline /path/to/legacy-run/data/suite.json \
  --candidate /path/to/batched-run/data/suite.json \
  --output /path/to/new-a31-comparison.json
```

比较要求相同 checkpoint/capture、原生 OM、设备、核数、tile、host/kernel/runner 源码、
warmup/测量次数；只允许 dequant 模式变化。逐位复核两次运行的 custom/native、timed tail、
postcheck 输出，报告原始样本、median/p95、workspace、legacy/batched 与 batched/native
耗时倍率，并同时保留两次 native 时间供检查环境波动。`PASS` 表示数值门槛通过；性能是否
有稳定收益须结合波动和后续测量判断。

## 设备 profile

完成未插桩的 A/B 后，可单独采集一个通过的 custom case；使用新目录，不覆盖验收结果：

```bash
"$MODEL_PYTHON" framework/custom_ops/draft_quant/test/profile_a31.py \
  --case-dir /path/to/batched-run/data/real/layer-0-gate_up/custom \
  --output-dir /path/to/new-a31-profile
```

入口使用安装环境中的 msprof，请求 task-based PipeUtilization，并恢复该次构建的隔离 OPP。
命令、日志和新 runner 输出保留在独立目录；profiled 输出还会与原已通过结果比较。
依据 [msprof 通用采集接口](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910/devaids/Profiling/atlasprofiling_16_0011.html)，
具体 9.0.0/310P 可用计数器以服务器工具输出为准；未返回的指标不当作零，也不改用模拟值。
profile 的计时不能参与未插桩 A/B。优先检查 Vector/Scalar、Cube、搬运与等待，决定下一步
是否需要进一步减少同步、调整 tile 或做双缓冲。

## 本地验证

本阶段初始 CPU 模型分别编译 legacy/batched，各执行 114 次单核/多核索引和累加检查，并核对两种模式
的源码级调用数；真实形状、N/K 边界、最后 group、FP32 相消及唯一输出 owner 均覆盖。
调度器的 CPU callback 测试检查 timed 循环没有 poison/readback，并检查尾部输入损坏及
后置 poison 暴露的未写输出确实失败。这些检查不代表 Ascend C 编译或 NPU 数值/性能通过。
当前扩展后的预取模型与回归范围见 [A3_2.md](A3_2.md)。
