# A5.0：scale broadcast 与完整 26 投影配对诊断

本阶段暂停 Head 和其他新算子开发，集中测试 `DFlashGroupQuantLinear` 的核内 scale
处理。默认生产 Draft、算子接口、checkpoint、NZ 格式与原生 OM 均不变。
**A5.0 CANN 编译、NPU bitwise、NPU benchmark、msprof 为 NOT_RUN**；CPU 模型通过
不能替代服务器验收。候选不会自动成为默认，`adoption=NOT_DECIDED`。

用户提供的历史背景：A4/A4.1 已通过全部形状 FP16 bitwise 验收；gate/up custom
约 3.67 ms、native 约 4.05 ms；KV M80 A-UB 约 3.1→1.27 ms（约 2.45×）。这些值
不是本轮 fresh paired baseline；A5 必须重新测量两个构建与各自 native。

## SDK 调查与候选边界

调查基于官方 `cann/asc-devkit` **v9.0.0，commit
`c8c1b9df6bb9cd61c09751c7ef414b89e06af274`**：

- [Brcb 接口](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/include/basic_api/kernel_operator_vec_brcb_intf.h)：
  每次 repeat 将 8 个 B16/B32 元素分别广播到一个 32B block。
- [dav_m200 Brcb 实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/basic_api/dav_m200/kernel_operator_vec_brcb_impl.h)：
  `dstBlkStride=1` 的 half 路径是 Vector 搬运、转置及恢复尾部，不是单条广播硬件指令；
  stride 其他取值的分支反而读取 scalar。当前候选仅用 `{1,8}`。
- [UB 常量](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/basic_api/utils/kernel_utils_constants.h)：
  `__NPU_ARCH__=2002` 的 256 KiB UB 中，固定临时区从 248 KiB 开始。
- [Mul 接口](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/include/basic_api/kernel_operator_vec_binary_intf.h)：
  用 mask/repeat/`BinaryRepeatParams` 的 FP16 双目乘法。

现有 batched 路径先用 4 次 Cast 把 signed INT8 NZ 的 K32 planes 写成 `[64,128]`
FP16 ND，再逐 N 读取 scale、调用 Muls。候选保留 Cast 和 ND 布局：

1. `Brcb(expanded, scale[group*64], 8, {1,8})`：64 scale → `[64,16]`，每行 16 个
   FP16 均为该行 scale 的相同位型。
2. PIPE_V 完成广播。
3. `Mul` mask=128、repeat=64、strides=`{1,1,0,tileK/16,tileK/16,1}`。
   src1 block stride=0，单行的 8 个 K16 blocks 复用同一个 scale block；repeat stride=1
   切换到下一个 N 行。destination/source0 的 repeat stride 与完整 ND 行长一致。
4. PIPE_V 保证 scratch 不被下一个 group 提前覆盖。K256 合成路径分别处理两个 group。

全程仍为 signed INT8 → FP16 Cast → **FP16 乘法反量化** → 原有 Cube FP32 全 K
累加 → 最后一次 FP16 输出。没有 GEMM 后乘 scale，没有 split-K，不改变 K tile 次序。
原有 raw prefetch、PIPE_ALL 和 Vector/Cube 同步保留。

| N64×K128 的源码 API 操作 | scalar baseline | broadcast 候选 |
| --- | ---: | ---: |
| Cast | 4 | 4 |
| 显式 sLocal.GetValue | 64 | 0 |
| Muls | 64 | 0 |
| Brcb | 0 | 1（8 repeats） |
| Mul | 0 | 1（64 repeats） |
| kernel 显式 PIPE_V | 2 | 4 |

**不能把上表当成硬件指令数或加速比。** dav_m200 的 Brcb 每个 repeat 内部还有 3 次
PIPE_V，即每 group 内部 24 次；另有内部搬运/转置、初始化及更多 UB 成本。它可能没有
收益，甚至变慢。实验目的是测证据，不预设广播一定更快。

## UB 成本与 KV M80 控制

候选新增：

| 区域 | 字节 | 用途 |
| --- | ---: | --- |
| broadcast 有效数据 | 2048 | 64×16 FP16 |
| broadcast 额外尾部 | 256 | dav_m200 Brcb 的最后一次 rear-data read/restore |
| SDK 固定临时区保留 | 8192 | 从 248 KiB 起不被 TPipe/Matmul 分配 |
| 总计占用原 Matmul 可用预算 | 10496 | 不是额外 GM workspace |

broadcast TBuf 共 2304 B，进入 kernel 时初始化一次。Host 从 Matmul UB 预算扣除全部
10496 B，TPipe 仅分配 2304 B scratch，把最后 8 KiB 留给 SDK。候选限定真实 UB=256 KiB；
不同布局明确失败，不能把 SDK 固定临时区与 Matmul workspace 混用。
`user_ub_bytes` 包含该保留预算，`DFLASH_GROUP_QUANT_SCALE` 分别列出 `broadcast_bytes`
与 `sdk_reserved_bytes`，避免把保留区误报成实际 TBuf 数据。

更多 UB 可能影响 SDK 自动 Matmul buffer depth，故比较报告同时保留两边的完整 Cube
计划。base M/N/K、单 owner 全 K 和完整 M 权重复用契约不放宽；不声称两边所有内部
调度都必然相同。

`(M,K,N)=(80,2560,2048)` 显式排除广播。配对 driver 强制两边都为 `a-ub`，其 StageA
模板在编译时排除广播分支，不分配 scratch 或 SDK 预留区。比较器要求 KV M80 的 UB、
workspace、Cube 计划完全一致。其他目标为 gate/up、down、Q、O、KV M32、FC M16/M64。

## 开关与原实现保留

- `DFLASH_DEQUANT_MODE=batched` 保留 A3.1 Cast；legacy 代码仍在。
- 新独立开关 `DFLASH_SCALE_MODE=scalar|broadcast`，**默认 scalar**。
- 配对 driver 固定 `DFLASH_KV_M80_MODE=a-ub`，两边使用同样的 core cap 和 pipeline。
- A5 driver 默认 `--pipeline prefetch`（已有 down 预取），可显式 `--pipeline serial`。
  普通 `run_server.sh` 的默认 serial/baseline 不变。
- 广播的服务器入口要求 `DFLASH_SUITE=a4`，必须全回归；不通过跳过其他形状获得 PASS。

两边都使用新的 `.build/a4-...`、`.runs/a4-...`、独立安装的 OPP。已有 OPP、证据、capture、
native OM 不覆盖；无需重新 capture 或 ATC。生成的 header/report 绑定 scale mode 和源码
哈希，Host 日志还必须匹配 scale 选择和 UB 预算，不能只看环境变量认定候选已生效。

## 服务器一键 A/B（含 msprof）

沿用现有 A4 环境和四份已验证产物。`A4_*` 若已设置则无需修改；下面路径是占位符，
必须指向原有 C16/C64 bundle 和原生 OM manifest。

```bash
git pull --ff-only
export MODEL_PYTHON=/path/to/existing/model/python
export CANN_ROOT=/usr/local/Ascend/ascend-toolkit/latest
export DEVICE_ID=0
export DFLASH_CORE_LIMIT=0
export A4_C16_BUNDLE=/path/to/existing/c16/manifest.json
export A4_C64_BUNDLE=/path/to/existing/c64/manifest.json
export A4_C16_NATIVE_OM_MANIFEST=/path/to/existing/c16/native-om.json
export A4_C64_NATIVE_OM_MANIFEST=/path/to/existing/c64/native-om.json

bash framework/custom_ops/draft_quant/run_a5.sh \
  --output-dir "$AI_RUN_DIR/a5-$(date +%Y%m%d-%H%M%S)" \
  --pipeline prefetch --warmup 5 --repetitions 30
```

流程：scalar 完整 A4 → broadcast 完整 A4 → 52 个真实投影的跨构建严格配对比较 →
两构建各 C16/C64 26 个投影的独立 msprof，共 **104 次 profiler replay**。耗时比只测
单个 gate/up 长；中间证据实时保存在新目录。任一构建或数值失败就停止后续流程。

相同输入使用 continuous-v1：预热 5、测量 30，报告每个投影的 raw samples、median/p95、
两边 native 时间、custom/native 比值、两边的 workspace 和 Cube/UB 计划。比较会重新
校验 actual-0、actual-1、benchmark-last、postcheck 的 bytes/hash，并与同输入 native
逐位比较；要求 finite、bits=0、ULP=0。原 guards/readonly 和 A4 的 36 合成形状必须通过。

如仅先完成未插桩 A/B，可显式加 `--skip-profiling`，报告保持 `profiling=NOT_RUN`。
不能将其当成完成了本阶段 profiling。为了排查运行顺序/温度漂移，可用新输出目录再次
执行 `--order candidate-first`；两次 raw evidence 都保留，不覆盖或挑选最好的一次。

## 看哪些文件

A5 总目录（`--output-dir`）：

- `scalar-server.log` / `broadcast-server.log`：构建/安装/完整 A4，包含实际 build/run 目录。
- `scalar-summary.txt` / `broadcast-summary.txt`：各自完整 A4 `data/suite.json` 的绝对路径。
- `comparison.json`：C16/C64 共 52 行；每行 custom/native 两边 raw 时间和 median/p95、
  bitwise 比较、launch 计划；`regressions` 列出任一 median/p95 变慢的投影。
- `comparison.json.totals.c16/c64`：各 **26 投影 median 之和、p95 之和**，并按完整形状
  分组（保留 5 层实际调用次数）；不能用 gate/up 一项替代。
- `profiles/<scalar|broadcast>/<c16|c64>/<projection>/`：保留原 msprof CSV 和 profile.json。
- `suite.json.profile_pairs`：52 对 profile，按同 gear/name 配对原始 Task、Cube、MTE、
  Vector/Scalar 字段（SDK 有才记录）；缺失列保持缺失/NOT_FOUND，不补零。

**sum(projection p95) 不是整次调用的 p95；sum(projection median) 也不是完整 Draft
实测 median。** 本实验各投影独立 launch+sync，不含整图 scheduling、KV 更新、attention、
head、Decode。两档合计分别报告，未给定生产 C16/C64 分布时不假造加权端到端收益。
msprof 的 duration 只用于定位，不混入未插桩计时。峰值显存沿用 runner 的未测量标记，
不以 workspace 字节冒充峰值。

`status=PASS` 只表示正确性/工作流通过，**不表示候选更快，也不自动采用候选**。
需要同时审阅各形状回退、两档 26 投影合计、native 差距、顺序复测波动与 profiler。
若无收益，记录失败的性能假设并保留 scalar；N64/K256、N128/K128 在拿到本轮数据后
再作为独立小实验，不能与本轮 scale 改动混合归因。目前它们、W 双缓冲、PIPE_ALL 减少
及进一步 Vector/Cube overlap 都为 NOT_RUN / 未实现。

## CPU 回归范围

```bash
python -B -m unittest discover -s framework/custom_ops/draft_quant/test -p 'test_*.py'
```

真实 kernel body 的 CPU API 模型覆盖 legacy/batched、serial/prefetch、A-UB 与广播，
包含全部 A4 形状、K256 双 group、NZ/group/N 边界、FP32 cancellation、signed code、
多核 owner、输入只读和失败路径。模型模拟 Brcb/Mul 的索引及 FP16 舍入，验证边界和
数值关系；不模拟 SDK 临时区硬件时序或其 24 次内部 barrier，不声称 CANN 编译通过。
Host 回归检查独立开关绑定、10496 B 预算、KV M80 不变、完整 26 次合计、配对协议、
postcheck 即使重新哈希也不能掩盖数值差异、失败构建不得进入 profiling。
