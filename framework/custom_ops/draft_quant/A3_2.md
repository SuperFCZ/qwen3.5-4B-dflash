## 范围与开关

构建期 `DFLASH_PIPELINE_MODE=serial|prefetch` 与现有 dequant 模式独立记录。prefetch 只允许
与 batched 组合；legacy+prefetch 显式拒绝。host/kernel 使用相同生成配置 header，不依赖
运行时环境变量选择 tiling，也不改变 ACLNN 或 tiling 数据 ABI。

| 形状 | serial | prefetch 构建实际选择 |
| --- | --- | --- |
| A1 M16 K256 N64/128/256 | 整段 K256，单 raw bank | 同 serial |
| A1 M16 K512/1024 N64/128/256 | K128，单 raw bank | 双 raw bank、提前一个 K tile |
| gate/up M16 K2560 N19456 | A3.1 batched serial | 同 serial，作为回归与计时对照 |
| down M16 K9728 N2560 | A3.1 batched serial | 双 raw bank、提前一个 K tile |

N64 cyclic 分工、每个 owner 完整 K 归约、group128 的 FP16 反量化、FP32 L0C 累加、最终
一次 FP16 舍入及原生 OM bitwise 门槛保持不变。没有新增 shape、split-K、中间 FP16 部分和
或模型主流程接入。gate/up 也必须在新二进制下重新验收，不能由旧 PASS 推定新构建通过。

## 数据与同步生命周期

每核为 INT8 q 和 FP16 scale 分配两份 raw bank，FP16 `[64,128]` W 仍只有一份。
每个 N tile 从 bank 0 开始，不跨 N tile 预取：

1. 搬入 group 0，设置 MTE2→Scalar 与 MTE2→Vector ready 事件。
2. 等待当前 bank 的两个 ready 事件，保护 scale `GetValue` 和 q `Cast`。
3. 若存在下一 group，在另一 bank 发起其 q/scale DMA 并设置 ready 事件。
4. 用原 A3.1 的 4 次 Cast、64 次 Muls 和 2 次 PIPE_V 完成当前 group 的反量化。
5. 用 `V_S` 的 SetFlag/WaitFlag 完成当前 W 的 Vector 写入，再发出 Matmul 调用。
   这处等待不显式排空下一 group 的 MTE2 DMA。
6. 保留每次 `Iterate` 后的 `PIPE_ALL`，在复用单份 W、Matmul workspace 或旧 raw bank 前
   等待消费者完成。同一 N tile 的 L0C 持续存在，K 顺序递增，最后才 `GetTensorC`。

ready 事件会跨越 Matmul，必须用 `AllocEventID` 保留，不能用不占用 ID 的 `FetchEventID`。
各保留一个 MTE2_S/MTE2_V ID：先消费当前信号，再设置下一信号，最多一个预取在途。
正常退出和 Matmul 返回失败时均先消费在途信号，再释放 ID。V_S 使用立即 Set/Wait 的
临时 ID，不跨越库调用。

这是**原始 q/scale 的单步预取实验**，不是完整的异步 Matmul 流水。每轮末尾仍全流水等待；
库内部也可能等待 MTE2，提前排队的 raw DMA 还可能延迟当前 A 的搬入。源码只创造 raw
搬运与当前反量化重叠的机会，不能证明实际重叠比例或性能收益。是否进一步双缓冲 W、
减少同步或调整 tile，应由新的未插桩 A/B 与 profile 决定。

依据固定的官方 `asc-devkit v9.0.0` 源码：

- [TPipe 事件池实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/basic_api/kernel_tpipe_impl.h)：
  Alloc/Release 修改占用位，Fetch 仅查找空闲 ID。
- [FetchEventID 说明](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/FetchEventID.md)：
  连续未配对信号不能复用未保留的 ID。
- [Matmul UB ND 搬运实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/stage/copy_cube_in/copy_tile_to_cube/data_copy_wrapper_using_ub_nd.h)：
  库内部也获取 MTE2_S/MTE2_V 等临时事件。
- [Matmul Iterate 实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/matmul_impl_base.h)：
  调度一次计算；本轮不靠返回值推断 UB 消费已完成。

源码审查不替代目标设备编译和运行验证。

## UB 与 launch 证据

| K128 每核用户缓冲 | serial | 选中 raw prefetch |
| --- | ---: | ---: |
| INT8 q | 8,192 B | 16,384 B |
| FP16 scale | 128 B | 256 B |
| FP16 W | 16,384 B | 16,384 B |
| 合计 | 24,704 B | 33,024 B |

增加的 **8,320 B** 从原先给 Matmul 的剩余 UB 中扣除，总 per-core UB 预算不增加。
`SetShape`、`SetOrgShape`、`SetFixSplit` 参数不变，`SetBufferSpace` 使用扣除后的预算；
SDK 返回的实际缓冲深度可能变化，不能声称整个 Cube tiling 二进制相同。
single-output-block / baseK 检查继续严格执行，系统 GM workspace 仍由 SDK 返回。

build 配置升级为 v3，launch JSON 升级为 version 3，新增 `pipeline_mode`、
`selected_pipeline`、`raw_banks`、`user_ub_bytes`、`matmul_ub_bytes`。每个 A1 case 和真实
projection 都检查实际选中路径、bank 数、UB 与构建一致。gate/up 在 prefetch 构建中
必须显示 `selected_pipeline=serial-v1`、`raw_banks=1`；down 必须显示 `raw-prefetch-v1`、
`raw_banks=2`。这些是 host 计划证据，不是设备重叠测量。
后续 A4 源码将 build/launch 升为 v4，并增加 full-M 字段；运行本页 A/B 时两边须用同一份
当前源码重新构建，比较器仍支持历史 v3 配对结果。

## 服务器完整 A/B

复用已通过的 `A2_BUNDLE` 和 `A2_NATIVE_OM_MANIFEST`，保持原 CANN_ROOT、MODEL_PYTHON、
DEVICE_ID 设置。在仓库根目录、同一空闲设备上顺序运行，期间不修改源码：

```bash
git pull --ff-only
export A2_WARMUP=5
export A2_REPETITIONS=30

# 当前源码下重新测量 A3.1 调度作为基线。
DFLASH_SUITE=a32 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=batched \
  DFLASH_PIPELINE_MODE=serial bash framework/custom_ops/draft_quant/run_server.sh

# 同输入、同协议的 down 预取候选；gate/up 继续 serial。
DFLASH_SUITE=a32 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=batched \
  DFLASH_PIPELINE_MODE=prefetch bash framework/custom_ops/draft_quant/run_server.sh
```

`a32` 默认 warmup=5、repetitions=30，使用 `continuous-v1`。每次创建独立 build、OPP、
runner 和 `.runs/a32-XXXXXXXX`，运行全部 9 组 A1/81 cases + 10 个真实 projection，
保留输入只读、guards、重复运行、timed tail、post-poison 及数值比较检查。
任一失败都不能进入性能结论。

保存两次输出的 `data/suite.json` 绝对路径，再执行：

```bash
"${MODEL_PYTHON:-python3}" framework/custom_ops/draft_quant/test/compare_a32.py \
  --baseline /path/to/a32-serial/data/suite.json \
  --candidate /path/to/a32-prefetch/data/suite.json \
  --output /path/to/new-a32-serial-vs-prefetch.json
```

比较器要求两次都是 A3.2/batched/continuous，同捕获输入、原生 OM、设备、源码、core cap、
实际核数、tile 和计时次数；只允许 pipeline 模式变化。检查全部 gate/up 对照仍为 serial、
总 UB 预算相同，并重新读取 custom/native 两次 correctness、timed tail、postcheck 文件
逐位比较。输出各 case 的原始样本、median/p95、`serial_to_prefetch_median_ratio`、
`prefetch_to_native_median_ratio`、两次 native 时间和 workspace。
旧 A3.1 batched suite 不能直接充当本次 baseline，因为源码不同。

比较 JSON 的 `PASS` 只说明数值与证据门槛通过。检查五层 down 是否稳定改善、p95 是否恶化、
gate/up 与两次 native 对照是否漂移；必要时反向顺序测量一对新目录。没有稳定收益时继续
保留 serial，不能因使用双缓冲就宣布优化成功。
