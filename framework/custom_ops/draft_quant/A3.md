# A3 第一版：按 N tile 多核化

用户已确认 A2 全部通过。本版只改变核间 N tile 分工，**A3 的 CANN 编译、NPU 正确性和
耗时仍待服务器验证**。继续使用同一个 `DFlashGroupQuantLinear` ACLNN 签名、tiling 数据
结构和 A1/A2 形状集合，Qwen/DFlash 主流程没有改动。

## 调度与数值契约

Host 用 `PlatformAscendC::GetCoreNum()` 获取 310P 耦合架构的可用 AI Core 数。设 N64 tile
总数为 T，启动核数 B 为 `min(T, available_cores, 可选构建上限)`；可用核数为 0 时明确失败。
上限 0 表示自动选择，上限 1 用于单核对照。核 b 用 `GetBlockIdx()/GetBlockNum()` 处理：

```text
tile_index = b, b+B, b+2B, ... < T
column_begin = tile_index * 64
```

每个 tile 恰好一个 owner，各核任务数最多相差一个。若设备返回 8 个可用核，gate/up 的
304 个 tile 每核 38 个，down 的 40 个 tile 每核 5 个；8 只是示例，不是硬编码核数。
N64 的 tiny 自然只启动一个核。kernel 在建立 MatMul/UB 前检查空闲或越界 block。

保留 A2 的 `SetShape(16,64,tileK)`、全局 A/C stride、局部 B stride，以及最终 Cube tiling
检查。核间分工由外层 N 循环负责，每核 MatmulApiTiling 仍描述一个计算 tile。每核拥有独立
UB、MatMul 对象和 L0C 累加器；系统 workspace 继续使用 SDK 返回的整算子预留大小，
没有添加共享的用户 GM workspace。

K=256 保留 whole-K `IterateAll`；更大 K 保留 K128、每 group FP16 scale、signed INT8→FP16
反量化、同一 FP32 累加器归约全部 K、最后一次 FP16 舍入。没有 split-K、原子累加、归约
重排、tile 调整、预取或双缓冲。

接口/初始化依据官方 v9.0.0 的
[GetCoreNum](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/GetCoreNum-143.md)、
[GetBlockNum](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/GetBlockNum.md)、
[MatMul 注册实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/kfc/kfc_register_obj.h)
和 [系统 workspace](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/docs/api/context/GetLibApiWorkSpaceSize.md)。
耦合架构的注册路径对本核对象调用 Init；这里保留原 MatMul 和系统 workspace 接口。
静态源码核对不能代替 310P3 上的编译/执行。

## 服务器运行

复用已经通过 A2 的 capture 和原生 OM，**无需重新采集或重新导出原生 OM**。本版修改了
host/kernel，必须重新 build/package/install；`run_server.sh` 每次使用新的隔离 OPP 和 runner。

```bash
git pull --ff-only
export CANN_ROOT=/usr/local/Ascend/ascend-toolkit/latest
export MODEL_PYTHON=/path/to/existing/model/python
export DEVICE_ID=0
export A2_BUNDLE=/path/to/passed-a2/capture/manifest.json
export A2_NATIVE_OM_MANIFEST=/path/to/passed-a2/native/native-om.json

DFLASH_SUITE=a3 DFLASH_CORE_LIMIT=0 bash framework/custom_ops/draft_quant/run_server.sh
```

A3 一次构建后运行：A1 的九种形状/81 个 case、A2 的五层 gate/up/down 共十组真实投影，
以及所有 custom 调用的 launch 记录验证。任意数值、只读、guard 或 launch 检查失败都返回
非零。真实投影仍以 custom↔原生 OM **FP16 bitwise 相等**为门槛。

可用下面的方式构建同一源码的单核对照，或限制为三个核检查除不尽的分工：

```bash
DFLASH_SUITE=a3 DFLASH_CORE_LIMIT=1 bash framework/custom_ops/draft_quant/run_server.sh
DFLASH_SUITE=a3 DFLASH_CORE_LIMIT=3 bash framework/custom_ops/draft_quant/run_server.sh
```

`DFLASH_CORE_LIMIT` 是**构建期**设置，仅修改 msopgen 工程中的 header 副本，源码默认值不变。
它不会在 Host Tiling 中读取环境变量，避免运行时改变限制却命中旧 tiling cache。改变上限
需要重新构建；配置和值对应的源码/header SHA256 保存到该次 run 的 `build-config.json`。

## 结果与比较

- `data/a1/suite.json`：A1 合成数值回归。
- `data/real/suite.json`：真实投影与原生 OM 对照，复用 A2 的原始输出、timing 和 workspace 报告。
- `data/suite.json`：A3 总结果、构建身份、每个 workload 的核数及各核 tile 分配。
- 每个 `runner.log` 的 `DFLASH_GROUP_QUANT_LAUNCH`：host 实际设置的 blockDim、平台核数、
  构建上限、M/K/N、tile 和系统 workspace。缺少此记录、记录冲突、核数与构建不符都会失败。

默认模式只有十个真实投影都使用至少两个核、且所有门槛通过，才输出 `PASS: A3 multi-core`。
`DFLASH_CORE_LIMIT=1` 的结果标为 `single-core-control`，其 `multicore_validation` 为 `NOT_RUN`。
launch 记录是 host 调度证据，不是设备 profiler 的并发利用率测量。

单核和多核都通过后，可比较两次 A3 的诊断耗时：

```bash
"$MODEL_PYTHON" framework/custom_ops/draft_quant/test/compare_a3.py \
  --single /path/to/single-run/data/suite.json \
  --multi /path/to/multi-run/data/suite.json \
  --output /path/to/new-a3-comparison.json
```

比较要求相同 capture/native-OM 身份、设备、host/kernel/runner 源码和计时协议；检查原始
输出哈希，并再做 single/multi/native 的逐位比较。报告原始样本、median/p95、workspace
及单核/多核 median 比值。比值表示独立调用的诊断结果，`status=PASS` 表示数值一致，不代表
达到性能预算。两次运行的设备负载、温度与波动仍需考虑；完整 Draft/Decode、进程峰值显存
和正式性能验收继续保留原来的 `NOT_RUN/NOT_MEASURED` 范围。

## 本地验证

```bash
python3 -B -m unittest discover -s framework/custom_ops/draft_quant/test -p 'test_*.py' -v
bash -n framework/custom_ops/draft_quant/run_server.sh
```

CPU 模型执行实际 kernel 源码，共 114 次单核/多核运行：A1 的 basis/dense/相消输入，两个
真实尺寸的稀疏输入；包含除不尽、核数大于 tile 数、反序调用、最后 K group 和最后 N tile。
逐元素要求写入恰好一次、owner 正确、输出等于独立 oracle；还检查各核 UB、K 迭代数、
累加器生命周期、输入只读与输出 guards。CPU 模型不模拟 NPU 并发或硬件流水。
