## 已知异常与尚未证明的原因

| 指标 | KV M32 | KV M80 |
| --- | ---: | ---: |
| 未插桩 custom | 0.468 ms | 3.228 ms |
| 未插桩 native OM | 0.323 ms | 0.470 ms |
| msprof Task | 406.6 μs | 3057.8 μs |
| msprof MTE2 | 77.2 μs | 2283.4 μs |
| msprof MTE2 ratio（原字段） | 0.223 | 0.893 |
| Cube utilization | 74.8% | 73.1% |
| baseM / planned L0A | 32 / 16,384 B | 80 / 40,960 B |

两者均为 7 核、N64/K128、32 个 N tile、20 个 K tile。M 增加 2.5 倍，用户给出的 MTE2
时间却约增加 29.6 倍，值得优先检查 A 的搬运。两组 L0A 数字分别等于 `M*128*2*2`，
均与 dbL0A=2 相符，**不能仅凭 40,960 B 就断言 M80 失去了 double buffer**。
原始 depthA1/B1、step、stall 时间线未提供，因此尚不能确定唯一根因。
各 pipe 可重叠；原 MTE2 ratio 不直接改算成 MTE2/Task，不把插桩 Task 与未插桩时延混算。

## CANN 9.0.0 源码调查与方案选择

核对官方 `asc-devkit v9.0.0`，commit `c8c1b9df6bb9cd61c09751c7ef414b89e06af274`：

- [默认 Matmul config](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/include/adv_api/matmul/tiling.h)
  中 normal config 的 vector ND2NZ 默认关闭。
- [V200 CopyTileToCube 路由](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/stage/copy_cube_in/copy_tile_to_cube/copy_tile_to_cube_using_ub.h)
  为 GM ND 和 UB ND 提供 `CopyND2NZOnTheFly` 路径。
- [默认 ND2NZ 搬运实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/stage/copy_cube_in/copy_tile_to_cube/data_copy_wrapper_using_ub_nd.h)
  在 FP16、K128、行宽 2560 的对齐分支中，沿 K 的 8 个 16-element slice 分别搬运。
  每条指令包含 M 个 32 B block，源行距 5120 B、srcGap=159。这是源码级搬运组织，
  不等于实测 DRAM 事务数。M80 的跨行细粒度读取是本轮假设，不是已确认硬件瓶颈。
- [dav_m200 DataCopy 实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/basic_api/dav_m200/kernel_operator_data_copy_impl.h)
  支持 GM→UB 的 blockCount/blockLen/stride；UB→L1 使用另一条搬运路径。
- [normal scheduler](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/scheduler/base/scheduler_norm.h)
  每次 `Iterate` 推进一个输出块，`enPartialSum` 控制累加器初始化。直接把 baseM 改成 32，
  但保留目前每 K-group 仅一次 Iterate 的代码，不能处理全部 M80 行，也不能保证独立的部分和状态。

| 可选方案 | 取舍 |
| --- | --- |
| baseM32，遍历 32+32+16 | 需独立且持续存在的 FP32 累加器、尾块和多输出块调度；简单外层 M 循环会重读/重复反量化权重，不采用 |
| 多 Matmul 实例共享 W16 | 有望复用 q/scale/dequant，但要管理多份 L0C/L1/UB 生命周期；可能重复 UB→L1 的 B 搬运，不是本轮最小候选 |
| 全局启用 vector ND2NZ | 该版本 UB ND 路由在此开关下返回不支持，当前 B 为 VECOUT ND，不能直接照搬 |
| 仅 KV M80 显式缓存当前 A tile 到 UB | 不改变输出块/K 归约，保持 B 的搬运和反量化次数；最小候选，用来隔离 GM 细粒度搬运因素 |

本轮选择最后一项。没有把减少 baseM 当作已实现的优化，也没有放宽 A4 的 full-M 检查。

## 候选改动与真实复用范围

显式构建开关 `DFLASH_KV_M80_MODE=baseline|a-ub`，默认 baseline。
只有 M80/K2560/N2048 选择 a-ub，其余形状始终调用原 A4 specialization。

1. 每个 N tile / K group，按原方式搬 q/scale、反量化一次 W16。
2. 当前 `A[80,128]` 用一次 2-D DataCopy 搬入 VECOUT UB：blockCount=80、blockLen=8、
   srcStride=152、dstStride=0（长度/stride 单位为 32 B）。每行有效搬入 256 B，共 20,480 B。
3. 复用原有 MTE2 等待和 PIPE_ALL，完成 A DMA 后才给 Matmul；本轮没有增加异步重叠。
4. Host AType 改为 VECOUT ND，A 的 Matmul 行宽改为 128；kernel `SetTensorA(LocalTensor)`。
   原 A4 为 GM ND、行宽 2560。B 仍是 VECOUT ND transpose，C 仍是 GM ND。
5. baseM=80、baseN=64、baseK=128、完整 K 的 FP32 累加和最终一次 FP16 输出均不变。
   每次 Matmul 后保留 PIPE_ALL，之后才复用 A/W/workspace；异常退出也完成候选缓冲消费者。

KV M80 用户 UB 从 24,704 增为 **45,184 B**，新增 20,480 B 从 Matmul 剩余 UB 中扣除，
没有新增用户 GM workspace 或完整 FP16 权重。SDK 可重新选择缓冲深度，不能声称 Cube
资源计划二进制相同。候选增加一次 GM→UB、改变后续 UB→L1 路径，可能让 MTE3 成为限制，
也可能没有收益；最终以未插桩 median/p95 和 profile 为准。

每 N tile 仍只做 **20 次**权重搬入/反量化，每份服务 **80 行**。A 在不同 N tile 间仍重读，
不宣称跨 N 的 A 复用。整个算子的逻辑 raw weight/scale payload 仍为 5,242,880 / 81,920 B；
A 各 N tile 的有效输入 payload 合计仍为 13,107,200 B。这些不是实际 HBM 流量测量。

build/launch 更新到 v5，tiling 数据布局 `full-m-v2` 不变。新增 `DFLASH_GROUP_QUANT_CUBE`
记录 A source/stride/staging 字节、baseM/N/K、depthA1/B1、stepM/N/Ka/Kb、dbL0A/B/C、
transLength、每 N tile 的权重反量化次数。host/kernel 配置 header 内容和哈希一致；
模式、shape、UB、full-M 复用或版本不符会拒绝，旧日志不能冒充新候选。

## 服务器：先 M80，再 M32，再完整 A4

复用 `.runs/a4-ziy26oQK/data/suite.json` 中记录的两档 capture/native manifest，
**无需重新采集或重新导出 native OM**。保留原 MODEL_PYTHON、CANN_ROOT、DEVICE_ID 和
四个 `A4_C16/C64_BUNDLE`、`A4_C16/C64_NATIVE_OM_MANIFEST` 变量。若新 shell 丢失变量，
可从原报告 `inputs.c16/c64.bundle.path`、`inputs.c16/c64.native_om_manifest.path` 恢复。
两次必须使用相同 device、core cap、dequant、pipeline、源码和数据，顺序运行、不同时抢占 NPU。
以下示例假设原 A4 为 serial；若原报告 `build.pipeline_mode` 为 prefetch，两条命令均改为
`DFLASH_PIPELINE_MODE=prefetch`，保留此前验证的 down 路径。

```bash
git pull --ff-only
export A2_WARMUP=5 A2_REPETITIONS=30

DFLASH_SUITE=a41 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=batched \
DFLASH_PIPELINE_MODE=serial DFLASH_KV_M80_MODE=baseline DFLASH_A41_STOP_AFTER=full \
  bash framework/custom_ops/draft_quant/run_server.sh

DFLASH_SUITE=a41 DFLASH_CORE_LIMIT=0 DFLASH_DEQUANT_MODE=batched \
DFLASH_PIPELINE_MODE=serial DFLASH_KV_M80_MODE=a-ub DFLASH_A41_STOP_AFTER=full \
  bash framework/custom_ops/draft_quant/run_server.sh
```

每次新建隔离 OPP，按顺序执行：

1. `data/kv80`：只执行 C64 的五层 KV M80，与原生 OM 严格 bitwise 对照。
2. 通过后才执行 `data/kv32`：C16 五层 KV M32。
3. 通过后才执行 `data/full`：原完整 A4，36 个合成形状/351 cases + C16/C64 52 个真实投影。

任一前置阶段失败，后续不运行。可将 **两边** `DFLASH_A41_STOP_AFTER=kv80` 先做快速隔离，
或设为 kv32；这时报告 `full_a4_regression=NOT_RUN`，不能当作完整 A4 通过。完成快速试验后，
使用两个新目录运行 full。默认两条命令已自动按要求排序。

这里使用显式 subset 入口做前置诊断，报告标为 SUBSET；完整 A4 的精确 case inventory、
bitwise/有限值/重复性/guards/输入只读/timed-tail/post-poison 门槛都未放宽。
baseline 也要用当前源码重新构建，不能拿原 A4 数字直接计算本轮收益。

保存两次打印的 aggregate 路径，比较：

```bash
"$MODEL_PYTHON" framework/custom_ops/draft_quant/test/compare_a41.py \
  --baseline /path/to/a41-baseline/data/suite.json \
  --candidate /path/to/a41-a-ub/data/suite.json \
  --output /path/to/new-a41-comparison.json
```

比较器要求两边 stop-after 一致，逐位重查 custom/native 的 correctness、timed tail 和
postcheck。输出全部原始样本、median/p95、两次 native 对照、workspace、Cube 计划；
非目标形状的缓冲/tiling 计划变化直接拒绝，median/p95 变慢分别标记，不能静默略过。
完整运行同时比较先行 KV 子集和完整 A4 中每个 projection 的计时，不把两种顺序的数据混合。
`PASS` 仅表示数值/证据通过，不是自动性能晋级。
