## 本轮只改变 K tile

新增 `DFLASH_K_TILE=128|256`，默认 128。A/B driver 两边均强制 Broadcast + batched、
KV M80 A-UB；相同 core cap、pipeline（默认沿用 prefetch）和输入，warmup=5、repetitions=30、
continuous-v1。Scalar 回退仍可单独使用，普通 A4 默认 Scalar/K128 不变。

| 路径 | K128 构建 | K256 构建 |
| --- | --- | --- |
| gate/up、down、Q、O、KV M32、FC M16/M64 | streamed K128 | streamed K256 |
| KV M80 `(80,2560,2048)` | A-UB、Scalar scale、K128 | 完全保持相同路径 |
| 原始 global K=256 合成形状 | whole-K256 IterateAll | 同左 |
| 六个 M80 K512/1024 N64/128/256 | streamed K128 | 显式 fallback K128 |
| 其他 A4 合成形状 | streamed K128 | streamed K256 |

N64、N cyclic 多核分工、raw prefetch 的启用形状与 bank 数不变。仍只有一份 W16 buffer，
不增加 W 双缓冲，不移动/删除 PIPE_ALL 或其它 fence。K tile 更大自然减少迭代/搬运次数，
但不改变每次迭代的同步组织；不能将收益归为独立的同步优化。

K256 的 raw NZ 为 `[8,64,32]`，FP16 B 为 `[64,256]`。8 次 Cast 后，对 group 0/1
分别取 `S[kBegin/128+group,n]`，分别广播并乘到 K 范围 `[0,128)` / `[128,256)`。
Mul 的 ND repeat stride 从 8 变为 16 个 32B blocks；两个 group 保持各自 FP16 舍入。
FP32 C 累加器沿全 K 存续，没有中间 FP16 partial sum、split-K 或 CPU fallback。

## CANN 9.0.0 / 310P3 的 tiling 合约

依据固定 v9.0.0 SDK：

- [Matmul tiling 概念](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0038.html)：
  SetShape 控制单次计算，SetFixSplit 请求 base shape，不能把请求值当作最终返回值。
- [MatmulApiTiling 实现](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/tiling/matmul/matmul_tiling_base.cpp)：
  读取平台 L1、L0A/B/C、UB；SDK 可调整计划，也可能失败。
- [norm scheduler](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/scheduler/base/scheduler_norm.h)
  和 [MDL scheduler](https://gitcode.com/cann/asc-devkit/blob/v9.0.0/impl/adv_api/detail/matmul/scheduler/base/scheduler_mdl.h)：
  ScheduleOnce 的 enPartialSum=false 分配 C，后续 true 延续部分和。

本轮对 streamed K256 请求 `SetShape(M,64,256)` / `SetFixSplit(M,64,256)`，并强制检查：

```text
singleCoreM = baseM = M
singleCoreN = baseN = 64
singleCoreK = baseK = 256
```

K128 对应强制等于 128。**不允许仅以 baseK 是 singleCoreK 的约数就接受**，例如
singleCoreK=256/baseK=128 会失败。错误的 M/N 拆块或 singleCoreK 同样失败。
原始 global K=256 的 IterateAll 合约保持原样，可接受 SDK 合法的 16 对齐 baseK≤256；
它不适用于本次 streamed K256。Host getter 仍用 non-const reference 兼容 CANN 9.0。

Kernel 外层始终按 K 升序：首 tile `Iterate(false)`，后续 `Iterate(true)`，所有 K tile
完成后才 `GetTensorC`。更大的 baseK 可能改变 Cube 内部加法分组，**不能仅凭 FP32
类型保证 bitwise 等价**。以同输入 native OM 的 bits=0、ULP=0 为唯一设备数值门槛。
若失败，保留 K128，不通过放宽验收或改成多次 FP16 求和绕过。

## 内存账本

Broadcast 保留 2304 B scratch 和 SDK 顶部 8192 B；A5.0 的边界和初始化不变。
以下是非 KV M80 的计划预算，不是实测访存量或峰值显存：

| 每核用户预算（含 SDK 保留） | K128 | K256 |
| --- | ---: | ---: |
| serial raw codes/scales + W16 | 24704 B | 49408 B |
| prefetch raw 双 bank + 单份 W16 | 33024 B | 66048 B |
| Broadcast scratch + SDK 保留 | 10496 B | 10496 B |
| serial 合计 / Matmul 可用 UB | 35200 / 226944 B | 59904 / 202240 B |
| prefetch 合计 / Matmul 可用 UB | 43520 / 218624 B | 76544 / 185600 B |

UB 总计仍为 256 KiB，TPipe 实际分配不得覆盖从 248 KiB 开始的 SDK 临时区。
KV M80 不进入 Broadcast/K256，其 A-UB `[80,128]` 与所有原预算保持不变。

当 baseK=256：L0A 单块 `M*256*2`，M16/32/64/80 分别为 8192/16384/32768/40960 B；
L0B 单块 `64*256*2=32768 B`；L0C FP32 单块 `M*64*4`，与 K tile 无关。
L1 按 `A块*depthA1+B块*depthB1` 记录，L0A/B/C 分别乘 SDK 返回的 dbL0A/B/C。
例如 64 KiB L0A 无法容纳两份 M80×K256 的 A；SDK 必须选择兼容的 depth，否则拒绝。

Host 记录每级实际返回计划及平台容量，streamed K256 对非法 depth 或超容量明确失败。
并保留 SDK 的 GetTiling 与 shape/base 校验，不强制手工改写 TCubeTiling。
日志新增 `DFLASH_GROUP_QUANT_K_TILE`：requested/selected tile、L1/L0 planned bytes/capacity。
比较器核对日志、构建 header、runner tile_k；KV M80 的原 Cube/UB/workspace 必须一致。

|---|---:|---:|
| 无插桩 Draft median | 17.1953 ms | 31.2091 ms |

### 可从源码确定的事实

- 以服务器已验收的生成配置 Broadcast/batched/K256 为准，不能用仓库 tracked header
  中的 Scalar/K128 默认值反推生产配置。Broadcast 分支没有逐 N 的 scale GetValue/Muls。
- Group128 的 FP16 scale 字节数只是 INT8 weight 的 1/64，即 1.5625%。不能据此说
  scale 指令便宜：Brcb 是软件展开。此前固定 v9.0.0 的 dav_m200 源码审计记录其每
  8-repeat 调用内部还有 24 个 PIPE_V；本轮没有重测当前 Kernel 内各 Pipe 的等待。
- `CopyRawTile()` 在 K256 下分别发出 8 次 K32-plane DataCopy 和 2 次 GN scale DataCopy。
  随后 8 次 Cast、2 次 Brcb、2 次 FP16 Mul；kernel 显式 PIPE_V 共 6 次/ktile。
- Gate/Up 不满足 `DFLASH_GROUP_QUANT_PREFETCH` 谓词，即使构建 pipeline=prefetch，
  Gate/Up 仍是 serial：每个 K tile 前后共有三处 PIPE_ALL（本核全流水），N tile 结束另一次。
- Down 可用两份 INT8/scale raw bank，但 FP16 W16 仍只有一份。每次 Iterate 后仍
  PIPE_ALL，因此并没有实现下一 tile 的反量化与当前 Cube 的完整并行流水。
- 当前 B tile 已被全部 M16 行共享；不同 N tile 的权重不同，无额外跨 N 权重复用可凭空省掉。
  每个 N owner 独立完成全 K，L0C 保留 FP32 partial sum，只在该 N tile 完成时输出 FP16。
- A 来自 GM。每次调用都 SetTensorA/B、Iterate；A 的跨 N 重载量和库内部 ND 搬运值得查，
  但逻辑请求字节不等于 DDR 实测流量，L2/Matmul 缓存会影响实际带宽。

| N64/K256 账本（全 kernel 合计，非单核） | Gate/Up | Down |
|---|---:|---:|
| M/K/N | 16/2560/19456 | 16/9728/2560 |
| N tiles × K tiles | 304 × 10 | 40 × 38 |
| Iterate 次数 | 3040 | 1520 |
| 最忙核 tile 次数（7 核时） | 440 | 228 |
| INT8 payload | 49,807,360 B | 24,903,680 B |
| GN scale payload | 778,240 B | 389,120 B |
| 若每调用重载 A 的逻辑量 | 24,903,680 B | 12,451,840 B |
| Cast API 次数 | 24,320 | 12,160 |
| Brcb / Mul API 次数（各自） | 6080 | 3040 |

按用户摘要，W8 的 weight+scale 逻辑字节/Task 时间约 24.56 / 26.91 GB/s，
不是 DRAM 带宽测量。相似的 per-tile 成本、频繁同步/调用与小粒度搬运是具体优化线索；
现有数据不能单独证明纯 MTE2、Scalar、Vector 或 Cube 哪个硬件单元占主导。
旧 A3.1 的 Cube 利用率不能直接代入当前 K256 整图 Kernel。

### 优先候选 1：Gate/Up 的二维批量 raw 拷贝

先只改变 `(16,2560,19456)` 的 CopyRawTile，保留 serial、N64/K256、UB 分配及所有
同步。将 q 的 8 条拷贝合为一次、两个 scale 拷贝合为一次，减少指令发射与地址计算。
使用现有对齐 DataCopyParams 路径，**不是 DataCopyPad 的字节 stride**：

- q：blockCount=8，blockLen=64，srcStride=19456-64=19392，dstStride=0。
- scale：blockCount=2，blockLen=4，srcStride=(19456-64)/16=1212，dstStride=0。
- 上述 len/stride 单位是 32B；源起点沿用原 nBegin/kBegin 公式，目标排列保持 `[8,64,32]`
  与 `[2,64]`。均在 uint16 范围内，但仍必须做 CANN9 实际编译及 NPU 边界/bitwise 验收。

API 拷贝调用从 30,400 降至 6080/层，**没有减少实际 weight/scale 字节数**，也不是承诺
5× Kernel 加速。验证 Scalar/MTE2 指令开销和 Task duration 是否下降，其他 Pipe 不应恶化。
已有 A4.1 的对齐 DataCopyParams 用法可复用，但不能把 half A 的设备 PASS 当作新 INT8
二维布局的 PASS。参数背景见[对齐 DataCopy 文档](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/82RC1alpha003/API/ascendcopapi/atlasascendc_api_07_0103.html)。

### 优先候选 2：独立开启 Gate/Up raw prefetch

单独将已验证 Down 的 raw 双 bank 路径扩到该 Gate/Up 形状，先用原 CopyRawTile 做 A/B，
避免和候选 1 同时改变。增加 16,640 B raw UB：用户预算 59,904→76,544 B，Matmul
剩余 UB 202,240→185,600 B（256 KiB 平台）；须记录 SDK 返回的 depth/db 与容量检查。
保留单份 W16、顺序 FP32 L0C 累加以及 Iterate 后 PIPE_ALL。假设是隐藏部分 raw MTE2
与当前反量化开销，并减少 serial 的前置全流水等待；它不是 W16/Cube 双缓冲。

风险是 next-raw DMA 与 Matmul 的 GM A 搬运争用 MTE2，或 UB 变小改变 SDK 的缓冲深度。
旧 Down K128 摘要约 6% 收益仅证明值得试，不是 Gate/Up K256 的收益预测。
完整 W16 双缓冲/Vector-Cube overlap 留到有等待证据、并确认 CANN9/310P3 的 B 消费完成
事件和 Iterate 异步语义后再设计；不能直接删 PIPE_ALL。N/K 大 tile 也会改变 L0B double
buffer 与 K 加法分组，不在这两项最小候选里同时修改。

### 同语义 Native W8 对照与最小后续工作包

当前两份 profiler 分别是 FP16 与 custom A-only，并没有同形状 Native W8 的逐轮时间。
历史 A5.1 同输入 isolated 配对和 off/a 全图结果只能作为各自口径证据，不能把其时间
直接移到当前 immutable-weight 整图。FP16 checkpoint 不能替代 Native WeightQuant golden。

下一轮若实施，先选 C16 的 `layer-0-gate_up`，复用已验收 A4 capture 和其 Native W8
WeightQuant OM：核对 x、signed INT8 NZ、GN scale、N/K/group128 及哈希完全相同。
保留 A5.1 OPP，候选各建独立 OPP/目录；baseline/candidate/native 都 warmup=5、reps=30，
分别记录 median/p95 与单独 msprof，检查 bits=0、ULP=0、guards、readonly、repeat、
timed-tail/postcheck。先 1 层 Gate/Up，再五层 Gate/Up；有收益后才完整 A4 回归及整图验证。
原 `run_a2.run()` 已支持 case_filter，可复用其严格比较器，但 CLI 尚无该筛选参数。
本轮只实现离线分析，不提供尚未实现的候选构建开关或伪造可运行的硬件实验命令。

本节候选实现、设备正确性与性能结果均为 NOT_RUN；Native Golden、Source Lock 及 Kernel 不变。
